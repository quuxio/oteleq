# Repository quality and badges

## Current scope

CI validates Markdown, illustrative JSON/TOML syntax, diagnostic capture observers and the Rust comparator. The required Rust job runs formatting, Clippy, regression tests and a minimum 80% line-coverage gate over product `src/` files; integration-test code is excluded from that measurement. The documentation job tests the capture observers and enforces at least 80% line coverage separately for each eight-language capture module and the collection validator. CI uses fake witness fixtures and private subprocesses; actual otelc toolchain qualification uses the separate eight-language integration run. CI also checks the scalar generator, syntax discovery, harness materialisation, state observers, process limits and source preservation, with 80% coverage gates on each Python module. Real otelc execution is qualified separately; unobserved state and unsupported build contexts remain outside the claim.

The [Go package adapter](go-package-context.md) adds real compiler-backed package inclusion/type regressions, private library and sibling-main workers, imported named scalars, inactive-file accounting and source/module/helper refusal controls. `go_project.py` has its own 80% coverage floor. The report presenter validates the explicit repository/module-relative function binding; raw telemetry and the typed comparator still require the exact runtime function name. The maintained `generation-go-project-otelc` target supplies separate actual paired qualification.

Go input-identity regressions cover its module selector (`go.mod`), checksum file, runtime and imported policy sources. A module change or policy edit/addition must invalidate the frozen provider; `go.sum` alone does not fix which dependency versions and SDK policy implementation are compiled. The [exact-revision Go diagnostic](qualification/go-inputs-2026-10-20.json) covers one scalar case and its generated unittest over eight actual launches, with an independent value oracle and four changed-input controls which each refuse before application execution.

Go build regressions validate the fixed manifest, both executable hashes, selected compiler/tools and environment, source/SDK/dependency identities, resolved policy, module denominators and SDK replacement. Changed or missing data, symlinks, size limits, altered flags/selection and failed compilation cannot choose an application launch. The same helper supplies fixed capture and generated callers; generated reports retain its identities. `generation-go-build-otelc` separately qualifies actual generated/exported/shrunk suites, compiler-free detached replay, byte/argument/exit/signal preservation and refusal controls. Unit fixtures do not qualify another provider. Install the locked documentation tools and run:

```sh
rustup toolchain install 1.98.1 --profile minimal \
  --component rustfmt --component clippy --component llvm-tools-preview
rustup run 1.98.1 cargo install cargo-llvm-cov --version 0.8.7 --locked
make setup
python3 -m venv .venv
.venv/bin/python -m pip install --only-binary=:all: coverage==7.16.2
rustup run 1.98.1 make check PYTHON=.venv/bin/python
```

Use Python 3.12+ and Node 24/npm for these contributor tools. `make setup` installs locked Markdown tooling and TypeScript 6.0.3 for real compiler-API inventory regressions; it does not install dependencies into an application or provider. Rust 1.98.1 and matching LLVM tools are pinned in CI. A newer compiler may build the application, but its coverage instrumentation requires matching LLVM tools; do not assume Homebrew's current Rust is compatible with LLVM 22.

The validation dependencies follow otelc's locked Markdown tooling. `npm ci` disables package lifecycle scripts. GitHub Actions are pinned to full action commits. Document prose is kept on logical lines and relative documentation links are checked during delivery. `make lint examples` checks Markdown and illustrative syntax; `make docs-check` also runs observer/generation regressions, while `make check` includes Rust checks and coverage.

## Traffic badge

The traffic workflow runs from `main` in `quuxio/oteleq`, but checks out and updates `.badges/traffic.json` on the separate `traffic-badges` branch hourly and on manual dispatch. The README reads that branch's badge data. This keeps generated traffic commits outside protected application source. Counts cover GitHub's rolling 14-day window; failed API reads fail the workflow and cannot publish a zero-value substitute.

`TRAFFIC_TOKEN` stores the saved quuxio credential, explicitly authorised for persistence in this repository's Actions secrets on 8 October 2026. It is exposed only to the traffic-read step in this workflow. The badge commit uses the separate automatic `GITHUB_TOKEN` with `contents: write`. Actions are pinned to a full commit, and traffic maintenance commits do not rerun documentation CI.

This credential retains its original GitHub permissions; storing it as `TRAFFIC_TOKEN` does not narrow those permissions. Its value is absent from source, badge output and workflow logs. Traffic counts are unrelated to product adoption or behavioural equivalence.

## Main branch protection

The active `Protect main` repository ruleset blocks deletion and force pushes, requires pull requests, and requires current passing documentation/design, Rust comparator/coverage and SonarCloud checks from their configured GitHub Apps. There are no bypass actors. Pull requests must be up to date with main before merging; no second human approval is required for this personal repository. The separate `traffic-badges` data branch allows the existing badge updater to publish without bypassing main protection.

## Implementation quality

Generated typed observations use closed language codecs and retained fixture contracts. Contributor `make generation-check` runs the real C/C++/Rust/Go/Java workers and Python/Node graph controls, with an independent 80% floor for `typed_capture.py`. `make node-observer-check` runs the actual private Node observer under Node24 V8 coverage, with 80% line/function/branch floors. These implementation checks are separate from actual otelc qualification. The maintained default corpus also checks intentional/unexpected errors, unequal initial fixtures and application lexical bindings which shadow Node builtin names; the configured corpus retains a typed Unicode difference control alongside the raw-byte control.

The [roadmap](roadmap.md) defines the remaining core and adapter gates. Use the pinned rustup workflow above for reproducible coverage. A qualified non-rustup distribution can supply matching `LLVM_COV` and `LLVM_PROFDATA` paths through `COVERAGE_ENV`; verify that their LLVM version matches that compiler's instrumentation. Meaningful comparator, codec, process-isolation, source-preservation and incomplete-evidence regression tests are required. Native generator regressions require Clang with C11 and C++17 support (override `OTELC_CLANG`/`OTELC_CLANGXX` when needed). These compiler tests do not establish compatibility with an otelc adapter built for another LLVM distribution. Publish actual implementation coverage with language/component scope. Extend the shared defect corpus with changed results, globals, receivers and effects as each observation capability is delivered.
