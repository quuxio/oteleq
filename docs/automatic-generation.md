# Automatic paired test generation

oteleq now inventories source files and generates an external `unittest` suite for C, C++, Rust, Python, Java, JavaScript, TypeScript and Go. The suite compares **equivalence over these tests and observations**. It is a bounded diagnostic check with a generated caller, not a proof about every function or a shipping artefact.

## Build and run

Build otelc and its qualified compiler/runtime adapters first. Use its locked CPython 3.12 environment so the OTLP protobuf decoder and Python adapter agree. Build oteleq with Rust 1.98.1 or newer:

```sh
cargo build --locked
export OTELEQ_PYTHON=/absolute/path/to/otelc/.venv/bin/python
OTELEQ_CLI=/absolute/path/to/oteleq/target/debug/quux-oteleq

"$OTELEQ_CLI" plan --source /absolute/path/to/application \
  --otelc-root /absolute/path/to/otelc --workspace-parent /tmp
```

`plan` prints the new private workspace path. Set `OTELEQ_WORKSPACE` to that actual path, then generate and execute:

```sh
OTELEQ_WORKSPACE=/tmp/oteleq-run-actual-id
"$OTELEQ_CLI" generate --workspace "$OTELEQ_WORKSPACE"
"$OTELEQ_CLI" run --workspace "$OTELEQ_WORKSPACE" \
  --report-dir /absolute/path/to/new-report

# The retained suite uses Python's standard unittest framework for every language.
"$OTELEQ_PYTHON" "$OTELEQ_WORKSPACE/tests/test_equivalence.py"
```

The report directory must be new and outside the application, otelc and workspace. Generation never edits the application, its dependencies, manifests or locks. Workspaces remain available until explicit cleanup; there is no automatic deletion after a successful run.

The CLI embeds its adapter sources, so an installed binary does not depend on an oteleq source checkout. It still needs the selected Python environment, otelc build and language tools. Keep the same CLI and tool contents for replay; changing them requires a new plan. `cargo install --path . --locked` installs the CLI locally.

## Selection and inputs

All recognised files are inventoried by default. Use repeated `--language ID` to select a subset; the report records that selection. `--exclude 'qualified.pattern'` explicitly excludes matching function identities. Free entrypoints named `main`, Java static `void main(String[])` methods and native declarations without a source body are inventoried as excluded callers/declarations. Nested or instance methods named `main` remain blockers. Exclusions remain visible. No selected unsupported function becomes a passing skipped test.

Up to three distinct concrete scalar inputs per function are generated by default (`--cases 1` through `--cases 16` changes the budget). Integer inputs start with `0`, `1`, `-1`; unsigned inputs use nonnegative values. Booleans, floats and supported strings have their own deterministic pools. Multiple parameters use shifted pools rather than an exhaustive Cartesian product; duplicate concrete inputs are removed. Native attempts build only the lane being executed. Zero-argument functions have one case. JavaScript and unannotated Python parameters receive bounded scalar samples; those samples do not establish business preconditions or useful domain coverage.

The initial implementation supports synchronous accessible free functions, Java static methods and qualified Node async functions. Python/Node can observe supported returned objects and objects reachable through declared module globals/arguments. Native, Java, Rust and Go state capture supports accessible scalar globals. User-selected exclusions can narrow the run to that supported scope.

Constructors, receiver factories, nested callables, generic instantiations, pointer/buffer inputs, Rust Cargo features, multi-file native/Go build graphs, Python async/generator schedulers and arbitrary dependency fixtures need further adapter work. They remain named blockers or retained build failures. There is no fixture-factory configuration yet. The proposed [equivalence policy](../examples/equivalence.toml) is not consumed by these commands.

## Discovery and build boundary

| Language | Inventory | Generated execution |
| --- | --- | --- |
| C/C++ | Clang AST JSON | Private include driver; matched LLVM 22 compilation and otelc pass |
| Rust | Pinned `syn` syntax AST | Private appended driver; actual rustc and otelc Rust adapter |
| Python | Standard `ast` | Independent CPython caller and actual otelc monitoring adapter |
| Java | JDK `JavacTask` Tree API | Private javac classes plus separate JVM caller and actual agent |
| JavaScript/TypeScript | otelc's pinned TypeScript compiler AST | Private appended Node caller and actual loader; matched TypeScript baseline emission |
| Go | Standard `go/parser` AST | Private appended same-file caller and actual Go compile adapter |

These are syntax inventories. Compilation and runtime witnesses qualify individual runnable cases; syntax alone does not establish semantic types, build visibility or safe domain inputs. Parse/tool errors produce inventory blockers. Dependencies must already be available to the qualified local tools; generation does not install them into the application.

Java uses `-Xshare:off` in both lanes. C/C++ select fixed LLVM 22 locations or explicit `OTELC_CLANG`/`OTELC_CLANGXX`; metadata verifies the canonical selected directory. Set qualified `OTELC_RUSTC`, `OTELC_NODE`, `OTELC_JAVA` and `OTELC_GO` where defaults are unsuitable. Rust SDK/compiler distributions and Node native observer ABI must match. See [tool qualification](eight-language-capture.md#run). The real eight-language integration is qualified on macOS ARM64; Linux/Windows are not qualified by that result.

## What is compared

Every case runs twice without instrumentation and twice with telemetry enabled, in separate processes and independently copied writable projects. The same frozen inputs and harness bytes are used in both lanes. Source, snapshot, corpus, generator, CLI, Python/decoder and tool identities are checked; changed identities fail. Helpers are excluded by exact function selection.

The comparator checks exact application stdout/stderr and typed return/error plus before/after state bytes. Python graph observations retain object fields, reference aliases, cycles, arbitrary-size integers and float bits. Node observes plain objects/arrays through own data descriptors, preserving aliases, sparse-array properties, bigint and float bits; accessors, symbols and unsupported prototypes are incomplete observations. Opaque observer failures are not converted into application exceptions. Python exception graphs retain arguments, custom fields and causal links; Node observes supported Error own fields and excludes stacks. Exception traceback/stack objects and Java/C++ extra exception fields are outside scope; unrecognised native panic/error payloads fail capture. Native observers capture scalar value representations, without reading object padding. Java, Rust and Go use tagged scalar representations, including float bits where supported.

Global roots are source-declared top-level assignments/variables. Imported-module state, hidden fields, arbitrary receivers, filesystem/network effects, mutation-and-reversion between boundaries and concurrent schedules are outside this observation scope. Those limits appear in the evidence. This version does not implement an instrumented-off lane, automatic shrinking, HTML or JUnit reporting.

Telemetry is decoded separately. Each instrumented invocation must contain exactly the selected function identity and one complete root tree, with valid IDs/parent graphs, matching service/scope, zero loss/pending counters and finished export. Recursive span counts and escaping-error counts are runtime observations, not independently predicted call counts. Repeated counts must agree. A baseline that exports telemetry, missing instrumentation, missing observations, crashes, timeouts, output overflow, unstable repeats or source changes cannot pass.

Source snapshots are capped at 10,000 files, 8 MiB per file and 256 MiB in total. Symlinks and non-regular files are rejected. `.git`, `target`, `node_modules`, `.venv`, `__pycache__`, `build` and `dist` are excluded and recorded; functions in those directories are outside the inventory. `.h` defaults to C; C++ headers use `.hpp`, `.hh` or `.hxx`. Recognised JSX/TSX can still require unsupported runtime/build context. Generation is capped at 1,024 cases. Workers have a wall-time limit and captured-output limit, and their process group is killed on completion/failure. Application channels have a smaller comparator budget. This is trusted local execution, not a hostile-code sandbox.

## Reproduce the qualification

With all qualified otelc tools available, this runs the maintained eight-language scalar fixture, exercises the generated framework and exported replay, then checks that a changed global object is detected while the function return remains identical:

```sh
make generation-otelc PYTHON=/absolute/path/to/otelc/.venv/bin/python \
  OTELC_ROOT=/absolute/path/to/otelc REPORT_DIR=/tmp/new-generation-qualification
```

The fixture covers 24 matching cases/96 paired-control launches, eight generated framework cases, exported replay and three deliberately different state cases. It is diagnostic evidence with the declared observation scope. No original application/source tree is modified.

## Reports, replay and retention

`report.json` retains every case result, the complete selected/excluded/blocked inventory, source identity, observation scope and source-preservation result. Case directories retain the concrete corpus, generated source, build logs and hashes, launch vectors, raw application observations, runtime reports, OTLP protobuf/HTTP records, comparator bundle and JSON comparison. Partial results remain available if a later case fails.

Exit `0` requires nonzero completed cases and no selected blockers. `1` reports a reproducible difference; `3` reports incomplete evidence or a blocked strict gate; `4` reports a tool/build/protocol/identity failure. Argument errors use `2`. The existing workload comparator retains its documented exit-code contract. The generated `unittest` suite turns every selected blocker into a failing test.

```sh
"$OTELEQ_CLI" replay --workspace "$OTELEQ_WORKSPACE" --case case-id-from-corpus

# Inspect the copy plan, then explicitly retain a portable bundle.
"$OTELEQ_CLI" export-tests --workspace "$OTELEQ_WORKSPACE" \
  --destination /absolute/path/to/new-tests
"$OTELEQ_CLI" export-tests --workspace "$OTELEQ_WORKSPACE" \
  --destination /absolute/path/to/new-tests --apply

"$OTELEQ_CLI" clean --workspace "$OTELEQ_WORKSPACE"
```

Export copies the frozen application snapshot, tests, corpus, plan and instructions into a new destination. The exported suite runs against that snapshot and retains its original provenance. It can be incorporated into an application's repository by choosing a new subdirectory explicitly; it does not silently rebind tests to future application changes. Create a new plan to test changed application code. The destination refuses overwrites. Retained/generated boilerplate is MIT licensed; copied application source retains its own licence, and the oteleq implementation remains AGPL-3.0.

Cleanup requires the ownership marker and refuses unknown top-level files or edited snapshots/suites. Keep reports independently before cleanup. A retained workspace is not a guarantee that external toolchains or dependencies will remain available.
