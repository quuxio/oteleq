# Rebuilt Rust provider integration

<!-- markdownlint-disable MD013 -->

This work connects the rebuilt Rust SDK to oteleq. The SDK has retained standalone stock/woven builds, direct launches and a candidate owned preparation contract. Independent consumer records now cover preparation, ownership statements, host release and final SDK health. An owned process monitor supplies the separate live OS checks before release. Compiler/caller discovery, downstream receipt and actual generated qualification remain separate work. The existing qualified Rust compiler/LLVM profiles remain separate; this document does not admit a new generated runtime profile.

## Consumer components

`rust_tools.py` independently reads the existing `otelc.rust.compiler-tools` version-one record. The caller supplies its selected compiler, sysroot, host and actual version query before the record is read. Fixed compiler/bridge product paths and the complete SDK Rust source/manifest/lock denominator are reconstructed independently. Original bytes and file facts remain held. The reader imports no SDK implementation and executes no compiler or application.

`rust_protocol.py` validates the reserved `otelc.rust.protocols` version-one descriptor for the explicit `rust1981-owned-standalone-v1` profile. Source build1 selects sync-v1, native plan2 and health1; source build2 selects drop-v2, native plan3 and health5. All other prepared record versions remain1. Missing or extra fields, mixed profiles and boolean/float version substitutes refuse. Descriptor acceptance alone does not establish that an SDK implements execution.

`rust_inventory.py` binds function inventory1 and woven lifetime inventory2 to a caller-held original source catalogue. It checks all declaration identities, compiler names, byte ranges, flags, source digests and ordered denominators before applying the common source/function selectors. The inspector does not import target code. Selected async, expanded, closure and oversized function identities refuse; excluded declarations remain in the checked inventory.

`rust_lifetimes.py` independently validates drop discovery2, including original type declarations, local roles, available/unavailable layout facts, ownership sites, skipped bodies and unavailable foreign/container/opaque locals. Selection retains the original argument/return/layout shapes for explicit compiler acceptance or refusal. It cannot silently discard selected unavailable types. Its lifetime request hashes each complete unfiltered MIR body with sorted compact UTF-8 JSON, including unselected locals and ownership sites. Woven metadata must match the caller-held local/type map and every complete body fingerprint. The caller also supplies the independently selected compiler target.

`rust_source_build.py` binds the existing standalone source-build1/sync and source-build2/drop formats to caller intent captured before SDK application compilation. The caller supplies complete compiler-discovered dependency paths and independent original function/MIR inspection records. The reader holds their original bytes and file facts, the complete compiled policy, optimisation, matching compiler/bridge products and resource-capable runtime. It checks physical output boundaries before reading products. Cargo, task/service context and a missing lifetime selection remain explicit refusals.

`rust_build_recipe.py` independently reconstructs stock discovery/plain compilation, driver inspection/weaving, bootstrap compilation, original cwd and matched flags. Fixed request/inventory paths, complete original dependency channels, exact bootstrap bytes, both application products and all required command/stdout/stderr/result channels remain retained. Producer inspection must match the caller's earlier inspection; equal changed producer inspect/weave records cannot replace it. Drop weaving must match independently held full MIR bodies, local types and UTF-8 fingerprints. The closed manifest binds every original input and required request/inventory/product identity with exact JSON primitive types.

Compiler result records require a positive integer PID, zero exit and finite elapsed time within the 1,200-second consumer budget. Those records do not independently establish historical process execution, kernel ownership, environment provenance or complete compiler/sysroot closure. Required fixed channels are checked; this reader does not claim that optional compiler debug outputs are a complete product catalogue. Changed sources, records or channels still refuse after their original bytes are restored. Fresh decoded policy/manifest views cannot mutate accepted intent.

`rust_owned_build.py` independently binds the source-build1/2 application to the fixed version-one ownership envelope and C11 exec gate. Before SDK gate compilation, the caller freezes the already accepted source build, the original gate source and the selected resolved LLVM C compiler. The reader reconstructs the exact non-coverage gate command and compiler-database cwd, checks the complete six-file owned output denominator and binds full original source/compiler/image/record facts with exact JSON types. The original application manifest stays external. An envelope cannot choose a foreign source manifest, compiler or executable; rewritten/rehashed metadata and byte restoration cannot refresh accepted intent. Physical output aliases into original application/build/compiler/SDK inputs refuse.

`rust_prepared.py` freezes the complete runtime TOML/policy, literal arguments, lane, host-wait budget, selected Python spelling/resolved interpreter and closed SDK Python producer catalogue before preparation. Runtime selectors must match the compiled source/function/type selection; service/export/metric settings can change independently. The reader reconstructs the closed request, fixed image/argv/cwd and interpreter/producer preparation records. Only the bounded SDK-generated launch nonce is learned from output. Private mode0600 single-link records and the original mode0700 directory remain held; an in-progress two-link publication stays pending. The fixed isolated/no-site supervisor command requires accepted unused preparation. Later ownership checks reconstruct the same argv without refreshing the original records.

`rust_execution.py` binds the two start statements to caller-supplied actual supervisor/application identities and the fixed command. PID, parent, group, session, intended image, launch identity and pre-exec phase must all match. Release or completion before that binding refuses. The final reader retains the original host acknowledgement, zero diagnostic supervisor/child exits, complete execution record and fixed final health. The plain lane requires absent SDK plan/control/policy/health. Repaired records and restored bytes cannot replace accepted file facts. SDK `exec_verified=false` remains explicit: an intended image in a pre-exec statement is not a kernel image observation.

`rust_health.py` independently validates exact Rust health1 or drop-health5, PID, policy/compiled-selection digests, closed zero-loss engines and exporter units. Completed and censored drop counts stay separate; admission must equal their sum, with no live/pending/lost/invalid owners. Sampled span completions must match final exported span units. Downstream receipt and partial rejection remain unavailable in SDK health and need independent transport evidence. The existing C/C++ control/function/span/export checks are reused through an unchanged extracted helper; neither their accepted wire profiles nor their checks change.

`rust_session.py` connects these records to the shared executor's original deadline and actual `Popen` supervisor. It queries both live OS PIDs with the fixed bounded `ps` command plus process-group/session syscalls. Both must have the exact expected parent and separate private group/session before any host acknowledgement is published. Original start records are rechecked after the queries and before release. The host keeps private original start/release/finish observations, rechecks the real exit and final health, and cleans the child's separate group through success and failure. Shared native OS-query/cleanup helpers preserve the previous C/C++ operations and error handling.

Run `make rust-provider-check` for bounded records, ownership/refusal tests and separate 80% coverage floors, including existing native health/session regressions. A controlled two-Python-process gate tests real OS identities and release-before-marker ordering; it does not execute Rust or an SDK. Local sandboxes must permit the fixed `ps` query for this probe. All eleven Rust modules are embedded in the distribution and bound to the generator identity. Required CI also runs these tests through `generation-check`.

The file/metadata readers do not themselves perform compiler input discovery or establish compiler execution, whole dependency/sysroot closure, successful instrumentation of a requested ownership shape or downstream receipt. The caller must obtain and freeze its source/MIR expectations independently before SDK builds; the monitor must obtain actual live ownership before release. The controlled Python probe checks the monitor's OS path, while genuine Rust/SDK generated execution, direct telemetry and retained-route qualification remain required. No new generated execution backend is enabled.

## Required SDK preparation boundary

The reserved `otelc.prepared_rust` interface preserves the current direct-build contracts: `rust1981-standalone-sync-v1`/build1 and `rust1981-standalone-drop-v2`/build2. Its separate `rust-owned-build.json` version-one envelope binds the caller-selected original `rust-source-build.json` and the fixed `gate/gate.json`; its profile is `rust1981-owned-standalone-v1`. The original application build remains external and is not copied or rewritten. Actual SDK/provider qualification and full generated/retained integration remain required.

Preparation must be compiler-free, create a new single-use private runtime and bind a closed request/plan/prepared record to the caller's policy, original build, fixed image, literal arguments, bounded wait and fresh launch ID. Both baseline and instrumented lanes need the same host release boundary. The baseline has no linked SDK, SDK plan or health. The instrumented lane supplies its existing native plan2/3 and health1/5 explicitly.

The host must observe the real supervisor/application parent, group and session before release. SDK metadata must retain unavailable image/ownership dimensions accurately; the consumer makes its own kernel observations. Final execution rechecks original source, compiler/bridge/SDK products and policy/selection, and retains actual exit, health, loss and drain results. Metadata cannot choose executables, compiler flags, modules or extra filesystem reads.

The consumer then joins independently declared values/state, raw function/drop telemetry and closed health. Live collection and emission change independently in one unchanged process/build while tracing remains independent. Generated callers, replay, detached/framework suites, reduction and current-source promotion each need actual execution and refusal controls.

## Full Rust requirements

Standalone preparation is one integration step. Cargo targets/features, dependency and build-script inputs, complete compiler/sysroot closure, receivers and mutable values, generic instances, async/cancellation and richer ownership remain required by the [completion plan](completion.md). Unsupported requested capabilities must remain visible. A literal metadata test or one diagnostic workload cannot complete those requirements or establish shipping artefact equivalence.
